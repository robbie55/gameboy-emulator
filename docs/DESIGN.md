# DESIGN.md

Architecture decisions and rationale for this emulator. This is a **living document** —
record decisions here as you make them. Decisions already settled are logged at the bottom;
the open ones below are framed with their tradeoffs for *you* to resolve (consistent with
the learning approach in `CLAUDE.md` — the reasoning is yours to do, not to receive).

## Design principles

1. **Module boundaries mirror the hardware.** `cpu`, `mmu`, `ppu`, `timer`, `cartridge`,
   `joypad`, coordinated by `gameboy`. If you can't point at the chip a class represents,
   reconsider the class.
2. **Minimal dependencies.** SDL2 for I/O only. The emulation core is hand-written.
3. **Correctness is validated, not asserted.** Test ROMs are the source of truth (see TECH.md
   and README). "It looks right" is not a passing state.
4. **Abstract only where it earns its cost.** This is the central lesson of *C++ Software
   Design* applied directly: the cartridge/MBC layer deserves a clean polymorphic seam; the
   CPU dispatch and PPU inner loops are hot paths where a flat, boring implementation wins.
   Be able to justify every abstraction in interview terms.

## System synchronization (the first big decision)

Every subsystem advances in step with the CPU clock. Two models:

- **Instruction-stepped catch-up** — execute one CPU instruction, measure its T-cycles, then
  advance the PPU and timers by that many cycles. Simpler; gets games running fast.
- **Cycle-stepped (tick) accuracy** — every component advances one (or four) cycles at a time
  in lockstep. More accurate for mid-instruction timing effects; harder to write.

*Tradeoff:* catch-up is enough to make Tetris run and is the right v1 choice; some accuracy
test ROMs and a few games with tight timing eventually want finer granularity. **Recommended
v1 path: instruction-stepped catch-up**, with subsystems structured so you could tighten the
granularity later without a rewrite. Decide, then log it.

> **→ RESOLVED (2026-06-10): instruction-stepped catch-up.** See the decision log.

## Component decisions  *(all resolved 2026-06-10 — see the decision log below; reasoning retained here)*

**CPU opcode dispatch** — giant `switch` vs. a function/handler table. The `switch` is simple,
fast, and the compiler optimizes it well; a table is more data-driven but adds indirection.
Most first emulators use the switch. **→ RESOLVED: `switch` (v1, for now); no Strategy/injection.**

**Register pairing (AF/BC/…)** — union type-punning vs. explicit `bc()`/`set_bc()` accessors.
The union is popular but leans on murky aliasing rules; accessors are portable and trivial.
(See the gotcha note in `CLAUDE.md`.) Decide *why* before you decide which. **→ RESOLVED: explicit accessors (v1, for now) — union type-punning is UB + a host-endianness trap.**

**MMU read/write dispatch** — routing an address to its region. Resist the urge to make this a
hierarchy of handler objects; a flat dispatch on the high address bits is faster and clearer.
This is a textbook "don't abstract the hot path" case. **→ RESOLVED: flat concrete dispatch; MMU holds devices by concrete type (option A), edges one-way `mmu → device`.**

**Cartridge / MBC** — *this* is where polymorphism belongs. Define a cartridge interface
(`read`/`write`) and implement it per controller. v1 needs only ROM-only, but design the seam
now so MBC1/3/5 slot in later without touching the MMU. This is your Strategy-pattern moment. **→ RESOLVED: cartridge interface at TOP — the one sanctioned polymorphic seam.**

**PPU rendering** — scanline-based vs. pixel-FIFO. Scanline rendering is simpler and sufficient
for v1 and most games; the pixel FIFO is hardware-accurate and needed for certain effects and
stricter test ROMs. **Recommended v1: scanline**, FIFO as a possible v2 refactor. **→ RESOLVED: scanline (v1, for now); FIFO is top of the v2 list.**

| 2026-07-10 | Timer modeled as a **single 16-bit internal divider + falling-edge detector** (one counter, not two). `DIV` (`FF04`) is a **read-time projection** of the counter's upper 8 bits; a `DIV` write **resets the whole 16-bit counter** to 0 (not a normal store). `TIMA` is driven by a falling-edge detector on a **TAC-selected bit** of the counter ANDed with the TAC enable bit. Faithful to the hardware circuit, and reuses the PPU `STAT` "projection, not stored" pattern so a CPU write can't corrupt live state. T-cycle clocking keeps the timer in the same unit as `cpu.step()` / PPU dots (Pan Docs' 14-bit / M-cycle figure is the identical circuit at ÷4 — taps 1/3/5/7 there). **Interior — zero diagram impact.** *(Reload-delay quirk = separate row below.)* | Two independent counters (a DIV counter + a separate TIMA accumulator): simpler to write but **cannot reproduce the DIV-write / TAC-change glitches without bolting on special cases**, and diverges from the hardware (rejected). 14-bit / M-cycle internal representation matching the Pan Docs figure literally (rejected: forces a T→M conversion at every `advance` for zero behavioral gain) |

Interior — zero diagram impact | Model it in v1 (rejected: unvalidatable by the v1 gate; contained enough to add later) |
| 2026-07-10 | Timer `advance(t-cycles)` = **consume/step, per-T-cycle** (not batch-and-compute): walk the budget one counter increment at a time, evaluating `(tapped bit) AND enable` and firing on the `1→0` edge | Stopping *at* each event makes dropping a side effect (falling edge, `TIMA` overflow) structurally impossible — the same reason the PPU chose its consume model. Perf is a non-issue — `advance` gets ≤24 T-cycles, a cold ≤24-iteration loop; written for an arbitrary budget so it stays correct if stepping ever batches | Batch-and-compute the edge count arithmetically (rejected: compute-crossings — one missed boundary = a silent dropped edge) |
| 2026-07-15 | **Joypad interrupt (bit 4 / vector `0x0060`) deferred to v2 — v1 raises nothing**, and the joypad stores **no** previous-state / edge information | The interrupt sits *outside both v1 gates*: Blargg never touches the joypad at all (not "passes without it" — it never looks), and Tetris **polls** `FF00` rather than waiting on the interrupt. Interior — zero diagram impact | Raise bit 4 in v1 (rejected: unvalidatable by either v1 gate, and it forces previous-state/edge machinery no v1 consumer would read) |
| 2026-07-15 | **Input delivery = once-per-frame level *snapshot*, pushed `gameboy → joypad`; the SDL-key→button map lives in `main`, no intermediary module** | The SDL↔button translation must live wherever both vocabularies meet, and `main` is already that adapter (the host/SDL boundary that owns `gameboy`). A separate input module wouldn't *remove* the two-vocabulary knot — it would relocate it into a new box and add an edge: ceremony for a **shallow** axis (one fixed keymap; remap + gamepad are v2). A level snapshot re-asserts ground truth every frame, so it **cannot desync** the way a per-event setter strands a button on a missed `KEYUP` (window focus loss); the sub-frame resolution it drops is below human/Tetris relevance at 59.7 Hz. | 2026-07-15 | **Joypad stores the eight button lines in *logical* form (1 = pressed); the `FF00` read is a read-time group **multiplex** + a single active-low flip. Two select bits (5–4) stored; bits 7–6 read as 1; writes land only on bits 5–4** | The snapshot arrives logical from `SDL_GetKeyboardState` (1 = held), so storing logical makes the setter a **dumb copy** and confines the *only* polarity reasoning in the module to one read-time expression sitting next to the multiplex — impossible to half-apply. `FF00` is multiplexed (it never exposes all 8 lines at once), so the store is the internal button matrix, not a register copy, and the read *selects* one group's nibble. Reuses the PPU `STAT` / timer `DIV` "**projection, not stored**" pattern so a CPU write can't corrupt live input state. `FF00` is a **cold** register (polled a handful of times per frame), so read-time conversion cost is irrelevant — the choice is driven by single-flip correctness, not perf. Interior — zero diagram impact | Store active-low ("hardware form") to skip a read-time conversion (rejected: `FF00` is ice-cold so there's no perf win, it merely relocates the flip into the setter, and it invites a half-applied inversion); store one `FF00`-shaped byte (rejected: the register is multiplexed — it cannot hold all 8 lines at once) |
| 2026-07-24 | **Joypad holds *no* `InterruptController` dependency in v1** — stronger than "raises nothing" (row above): the ctor takes no controller, the class has no controller member, no `#include`. Supersedes the earlier "mirror the PPU/timer ctor exactly" intent | With no v1 raise, the injected ref was dead weight. Pan Docs confirms the joypad IRQ fires on a P1 bit 0–3 high→low transition *in the selected group* (with switch-bounce repeats) and its **only** real purpose is waking from **STOP** — which is out of v1 (Tetris never STOPs, Blargg doesn't exercise it). ### Default key mapping *(v1, for now)*

The host-key → Game Boy button map. It lives **only in `main`** (the SDL adapter — the sole place that pairs an `SDL_Scancode` with a button); the joypad never sees a scancode. Scancodes are *physical* key positions (layout-independent), read via `SDL_GetKeyboardState`.

| Host key | GB button | Group |
|---|---|---|
| `W` | Up | d-pad |
| `A` | Left | d-pad |
| `S` | Down | d-pad |
| `D` | Right | d-pad |
| `K` | A | action |
| `L` | B | action |
| `Enter` (Return) | Start | action |
| `Right Shift` | Select | action |

The button → bit-position layout of the snapshot byte is **not** duplicated here — it's defined once in the shared button-contract header (SDL-free, included by both `main` and the joypad) and mirrors the FF00 P-line order per Pan Docs (d-pad nibble = Down/Up/Left/Right at bits 3–0; action nibble = Start/Select/B/A). **Revisit trigger:** configurable keybindings or a 2nd input source (gamepad) — same trigger as the input-delivery row above; at that point this fixed table becomes a loadable config.
